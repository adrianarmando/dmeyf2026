1. Resumen Ejecutivo del Análisis

El archivo 620_WorkFlow_01_junior_grupoA-10_v2.ipynb representa la materialización del Problema #10 asignado al Grupo A dentro del marco colaborativo de la Maestría (DMeyF 2026): el desarrollo e integración de un mecanismo estocástico de Feature Engineering Intra-mes automatizado basado en Algoritmos Genéticos.

A nivel de estructura global, el pipeline conserva intactas todas las fases estándar del workflow de la cátedra: lectura de datos (DT), análisis de catástrofe e imputación (CA), corrección de Data Drifting por deflación e índices monetarios (DR), Feature Engineering histórico con lags y deltas (FEhist), partición temporal y Grid Search con LightGBM.

🔬 Las Incorporaciones Centrales en v2

  • Evolución Gramatical (gramEvol): Generación estocástica de expresiones algebraicas mediante una gramática formal en formato Backus-Naur (BNF).
  • LightGBM Univariado como Fitness: Función de evaluación rápida basada en el AUC de validación de un modelo de gradiente boosting entrenado sobre una única columna sintética.
  • Saneamiento de Bugs: Resolución explícita de 3 errores críticos presentes en scripts preliminares (doble mapeo gramatical, filtrado excesivo de NAs y evaluación errónea de genomas crudos).
  • Paralelización Multinúcleo: Uso de mclapply para evaluar la población final y extraer las mejores variables sintéticas.

⚠️ El Hallazgo Crítico Detectado

La inspección técnica profunda de las salidas de ejecución de v2 reveló un grave efecto colateral inadvertido:

Para computar el fitness en la Celda 46, se creó prematuramente la columna clase01 en el dataset. Al no ser eliminada antes del paso de FEhist (Celda 56), el motor generó deltas temporales del target: clase01_delta1 = clase01 - clase01_lag1. LightGBM aprendió a usar esta variable filtrada durante el Grid Search, alcanzando un AUC artificial de 0.999998 (Data Leakage total).

Saneamiento Metodológico: Los 3 Bugs Resueltos en la Celda 47

Uno de los aspectos más valiosos del código incorporado en la versión v2 es que documenta y resuelve explícitamente tres fallas lógicas complejas heredadas de intentos previos:

Bug 1: Doble Mapeo Gramatical

Error previo: La función de fitness llamaba a GrammarMap(expr, ...) dentro de fitness_gramEvol.

Corrección: GrammaticalEvolution() ya envía la expresión R completamente mapeada a la función evaluadora. Se eliminó la llamada redundante que generaba errores de conversión.

Bug 2: Descarte Hiperagresivo de NAs

Error previo: La validación any(!is.finite(valores)) descartaba cualquier fórmula que tuviera un solo NA.

Corrección: Esto borraba todas las variables de tarjeta Visa (que tienen NAs estructurales en clientes sin tarjeta). Ahora solo se descarta si todos los valores son inválidos o la varianza es nula.

Bug 3: Evaluación de Genoma Crudo

Error previo: Al extraer el Top 5, se pasaba el vector de enteros del genoma (poblacion_final[[i]]) directamente al eval().

Corrección: eval() sobre un vector de enteros no falla: entrenaba LightGBM con ruido aleatorio. Se creó evaluar_genoma() que mapea antes de evaluar.

A diferencia de los enfoques genéticos basados en strings simples o listas prefijadas, la versión v2 implementa Evolución Gramatical mediante una gramática BNF (Backus-Naur Form) compilada en tiempo de ejecución:

Definición de la Gramática BNF en R:

protected_div <- function(x, y) {
  res <- x / y
  res[is.na(res) | is.infinite(res)] <- 0
  res
}

protected_log_diff <- function(x, y) {
  res <- log(abs(x - y) + 1)
  res[is.na(res) | is.infinite(res)] <- 0
  res
}

string_vars <- paste(candidatas_GA, collapse = " | ")

",

6. Función de Aptitud: Evaluación Rápida Univariada

Evaluar cientos de árboles completos de LightGBM por cada individuo del algoritmo genético sería prohibitivo en términos de cómputo. La implementación de la versión v2 resuelve esto mediante una función de aptitud univariada ultra optimizada:

Estructura de fitness_gramEvol(expr):

fitness_gramEvol <- function(expr) {
  valores <- tryCatch(eval(expr, envir = dataset), error = function(e) NULL)
  if (is.null(valores)) return(1)  # costo máximo si la fórmula falla

  valores_finitos <- valores[is.finite(valores)]
  if (length(valores_finitos) == 0 || length(unique(valores_finitos)) <= 1) {
    return(1)  # costo máximo si no tiene varianza
  }

  dtr  <- lgb.Dataset(data = matrix(valores[idx_train], ncol = 1), label = y_train)
  dval <- lgb.Dataset(data = matrix(valores[idx_valid], ncol = 1), label = y_valid)

  modelo <- tryCatch({
    lgb.train(
      params = list(objective = "binary", metric = "auc",
                    learning_rate = 0.1, num_threads = 1, verbosity = -1),
      data = dtr, valids = list(valid = dval),
      nrounds = 50, early_stopping_rounds = 10, verbose = -1
    )
  }, error = function(e) NULL)

  if (is.null(modelo) || is.null(modelo$best_score) || is.na(modelo$best_score)) return(1)

  1 - modelo$best_score   # Costo a minimizar: menor es mejor (AUC alto -> costo bajo)
}

7. ⚠️ Diagnóstico Crítico: Target Leakage y el "Falso AUC 0.999998"

Al inspeccionar las salidas de ejecución reales guardadas en la Celda 79 de 620_WorkFlow_01_junior_grupoA-10_v2.ipynb, se detecta un resultado estadísticamente imposible en condiciones de modelado reales: 

Wed Sep 09 00:25:53 2026  64, 64, 0.5 niter 293 AUC 0.999998083525509
Wed Sep 09 00:26:21 2026  64, 64, 0.8 niter 205 AUC 0.999998281781491

Un AUC de 0.999998 en un problema de churn bancario es un síntoma indiscutible de filtración de la variable objetivo (Target Leakage / Data Leakage).

🚨 Cadena de Causa Raíz Identificada Paso a Paso:
  1. Paso 1 (Creación prematura en Celda 46): Para calcular el fitness del GA antes de tiempo, el autor ejecutó: dataset[, clase01 := ifelse(clase_ternaria %in% c("BAJA+1", "BAJA+2"), 1, 0)]. La columna clase01 quedó viva en el dataset.
  2. Paso 2 (Inyección inadvertida en FEhist - Celda 56): La celda de Feature Engineering Histórico define:
    cols_lagueables <- copy(setdiff(colnames(dataset), c("numero_de_cliente", "foto_mes", "clase_ternaria"))).
    En el notebook original (v01), clase01 no existía aún en esta fase. En v2, clase01 sí existía y no estaba en la lista de exclusión.
  3. Paso 3 (Creación de deltas del target): FEhist generó automáticamente: clase01_lag1, clase01_lag2, clase01_delta1 y clase01_delta2.
    En particular, clase01_delta1 = clase01 - clase01_lag1 contiene directamente la etiqueta del target actual.
  4. Paso 4 (Selección de features para el modelo - Celda 66):
    campos_buenos <- copy(setdiff(colnames(dataset), c("clase_ternaria", "clase01", "azar"))).
    Esta línea excluye clase01, ¡pero dejó adentro a clase01_delta1 y clase01_delta2!
  5. Paso 5 (Falso Aprendizaje Perfecto en Celda 79): Los árboles de decisión de LightGBM simplemente aprendieron la regla trivial sobre clase01_delta1, logrando predecir el target de validación 202107 casi al 100% de certeza.

Consecuencias Catastróficas en Kaggle / Producción:

En los datos del mes futuro (202109), la variable clase_ternaria no está informada (es el target que se busca predecir). Por lo tanto, clase01 es NA o 0, clase01_delta1 pierde totalmente su contenido informativo, y el modelo entrenado con este atajo predecirá probabilidades absurdas, resultando en un colapso total de ganancia económica y puntaje en Kaggle.

10. Recomendaciones Técnicas y Plan de Acción para el Grupo A

Para sanear completamente el workflow v2 y transformar el Algoritmo Genético en una ventaja competitiva real en Kaggle, se deben aplicar las siguientes medidas:

1. Corrección Inmediata del Target Leakage (Crítico)

Eliminar clase01 del dataset inmediatamente después de concluir el GA, permitiendo que se cree en su momento natural (Celda 65), o excluirla en FEhist:

2. Control de Sobreajuste con Canaritos

Las variables sintéticas generadas por evolución univariada pueden memorizar ruido histórico. Se recomienda implementar la Celda 60 (actualmente vacía: # No se implementa la reduccion...) agregando canaritos asesinos (variables aleatorias uniformes) y podando aquellas fórmulas GA cuya importancia quede por debajo del canarito mediano.

3. Alineación del Fitness con el Negocio Financiero

Actualmente el GA evalúa mediante AUC global. Sin embargo, la competencia premia la ganancia acumulada en los mejores 9.000 a 11.000 envíos. Adaptar la función de fitness para evaluar la ganancia acumulada en el punto de corte óptimo financiero ($p^* pprox 0.0256$) seleccionará interacciones mucho más rentables.

4. Limpieza de Sesión y Corrida End-to-End

Reiniciar el kernel de R (Restart & Run All) para limpiar las 14 variables acumuladas en memoria y garantizar que el dataset genere exactamente el Top 5 deseado. Completar las 50 iteraciones del Grid Search y generar los submits definitivos en exp/WF9199.
