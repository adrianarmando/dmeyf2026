1. Resumen Ejecutivo del Análisis

El notebook z621_WorkFlow_03_junior_grupoB.ipynb representa una evolución arquitectónica directa sobre z621_WorkFlow_01_junior_grupoB.ipynb. La estructura central del pipeline tradicional (Catastrophe Analysis, corrección de Data Drifting con índices monetarios, asignación de target binario, Grid Search de hiperparámetros y entrenamiento final) se mantiene intacta en su estructura matemática original.

Sin embargo, la versión 03 introduce un cambio cualitativo mayor: sustituye la pasividad del Feature Engineering tradicional por un sistema heurístico estocástico de búsqueda evolutiva (Algoritmo Genético Ampliado) que crea y valida empíricamente nuevas interacciones intra-mes usando un modelo rápido de gradiente boosting.

💡 El cambio conceptual fundamental:

Mientras que en v01 solo se creaban manualmente 2 variables fijas (kmes y mpayroll_sobre_edad), en v03 se explora de forma autónoma un espacio combinatorial de 0 imes 39 imes 6 = 9.360$ posibles interacciones numéricas intra-mes, evaluando cada individuo mediante un LightGBM univariado con Cross-Validation de 2 pliegues sobre 27 meses de historia bancaria.

4. El Gran Agregado: Feature Engineering con Algoritmo Genético (Celda 44)

La Celda 44 introduce la rutina FE_intra_GA_ampliado. Los algoritmos genéticos simulan el proceso de selección natural darwiniana (cruce, mutación, supervivencia de los más aptos) para navegar espacios de búsqueda inmensos de forma eficiente.

Flujo de Trabajo del Ciclo Evolutivo

  1. 1
    Población Inicial (=30$)

    Se generan aleatoriamente 30 individuos. Cada individuo es una terna compuesta por {var1, var2, operacion}.

  2. 2
    Evaluación de Aptitud (Fitness)

    Para cada individuo, se genera temporalmente la columna en el dataset y se calcula el AUC univariado promedio mediante validación cruzada (2 folds) con LightGBM.

  3. 3
    Selección Elitista (=15$)

    Se ordenan los 30 individuos de mayor a menor AUC y se conservan intactos los mejores 15 para la siguiente generación, asegurando que las mejores soluciones nunca se pierdan.

  4. 4
    Reproducción, Cruce y Mutación

    Para los 15 individuos restantes, se seleccionan parejas de la élite y se combinan (cruce: var1 del padre 1, var2 del padre 2, nuevo operador). Cada componente muta con un 30% de probabilidad (runif(1) < 0.3).

  5. 5
    Cierre Evolutivo y Adopción ( ext{ generaciones}$)

    Al completar las 8 iteraciones generacionales, se evalúa la población final y se seleccionan las **5 mejores variables absolutas** para ser inyectadas de forma definitiva en el data.table principal.

Los 6 Operadores Matemáticos Implementados

El algoritmo amplió los operadores de 4 a 6 respecto a versiones preliminares simples:

ratio

var1 / (var2 + 1)

Relación proporcional entre montos o transacciones, con suavizado +1 en denominador.

producto

var1 * var2

Interacción multiplicativa que intensifica señales conjuntas extremas.

suma

var1 + var2

Agregación de volúmenes o consumos entre canales bancarios paralelos.

resta

var1 - var2

Balance neto o margen diferencial entre ingresos, egresos o saldos.

log_ratio (Nuevo)

log(|var1|+1) - log(|var2|+1)

Diferencia logarítmica que estabiliza la varianza ante órdenes de magnitud dispares.

diff_pct (Nuevo)

(var1 - var2) / (|var2|+1)

Variación porcentual relativa normalizada por la magnitud de la base.

6. Función de Aptitud: Evaluación Rápida Univariada

Uno de los desafíos principales de usar Algoritmos Genéticos en Big Data es el costo computacional. Si se evaluara cada individuo con un modelo completo de cientos de árboles, el GA tardaría horas o días.

Diseño de fitness_variable_cv():

fitness_variable_cv <- function(dataset, nueva_var, k_folds = 2) {
  filas_train <- which(dataset %in% meses_training_ga)
  n <- length(filas_train)
  folds <- sample(rep(1:k_folds, length.out = n))

  aucs <- numeric(k_folds)
  for (f in 1:k_folds) {
    idx_valid <- filas_train[folds == f]
    idx_train <- filas_train[folds != f]

    dtr <- lgb.Dataset(
      data  = as.matrix(dataset[idx_train, nueva_var, with = FALSE]),
      label = as.numeric(dataset[idx_train, clase_ternaria] %in% positivos_ga)
    )
    dval <- lgb.Dataset(
      data  = as.matrix(dataset[idx_valid, nueva_var, with = FALSE]),
      label = as.numeric(dataset[idx_valid, clase_ternaria] %in% positivos_ga)
    )

    modelo <- lgb.train(
      params = list(objective = binary, metric = auc),
      data = dtr,
      valids = list(valid = dval),
      nrounds = 60,
      early_stopping_rounds = 15,
      verbose = -1
    )
    aucs[f] <- modelo
  }
  return(mean(aucs))
}
Detalles Críticos de Rendimiento:
  • Univariado puro: El dataset de entrenamiento contiene una única columna (la variable candidata). Esto permite que cada árbol de LightGBM entrene en fracciones de segundo.
  • Período Temporal de 27 Meses: Utiliza los meses 201901 a 202103 para asegurar que el poder predictivo sea robusto en el tiempo y no dependa de un mes atípico.
  • Parada Temprana Estricta: nrounds = 60 y early_stopping_rounds = 15 evitan iteraciones innecesarias si la variable no aporta señal.

9. Plan de Acción y Próximos Pasos para el Grupo B

1. Potenciar el Algoritmo Genético

Actualmente el GA corre 8 generaciones con 30 individuos en 4.5 minutos. Dado el bajo costo temporal, se recomienda:

  • Aumentar a 15 generaciones y población de 50 individuos.
  • Probar operadores no lineales adicionales, como sqrt(abs(var1)) * sign(var1) o ratios estandarizados con desviaciones estándar históricas.
  • Seleccionar las mejores 15 variables élite en lugar de solo 5.

2. Control de Sobreajuste con Canaritos

Las variables generadas por GA pueden memorizar ruido si solo se evalúan de forma univariada. La Celda 55 (Canaritos Asesinos) está actualmente sin implementar (# No se implementa la reduccion...).

  • Inyectar 10-20 variables aleatorias (canaritos) tras el paso del GA.
  • Eliminar cualquier variable sintética cuya importancia quede por debajo del canarito mediano.

3. Sinergia con el Grupo A (Ensamble de Modelos)

El Grupo A centró su esfuerzo en deltas históricos y lags de orden 1 y 2 (Workflow 9100). El Grupo B aporta interacciones combinatorias intra-mes creadas por GA (Workflow 91112).

  • Al ensamblar (blending) las probabilidades de ambos modelos, la diversidad de señales no correlacionadas suele aportar entre 15 y 30 millones adicionales de ganancia acumulada en el test set de Kaggle.

4. Optimización de la Métrica de Búsqueda

Actualmente el GA utiliza AUC como métrica de aptitud en lgb.train. Sin embargo, el objetivo del negocio es la ganancia en los mejores 9.000 a 11.000 clientes.

  • Explorar en futuras iteraciones una función de fitness basada en la ganancia acumulada en el punto de corte óptimo (^* pprox 0.0256$) para alinear la evolución directamente con el retorno financiero.
